# kwin-mcp 0.11.0 goldens

These files record what kwin-mcp **0.11.0** (commit `7a5d781`) did, so the 1.0 tests can compare the new tools against the old behaviour without depending on the new implementation. They were captured once and are not regenerated by the suite. Every value in them is deterministic: timestamps, pids, temporary paths, socket names and window UUIDs were removed or replaced with placeholders.

| File | Content | Used by |
|---|---|---|
| `<scenario>.json` (27 files, `down_move_up.json` included) | Raw input event timelines that a GTK3 probe observed while a 0.11 input tool ran | QA-INP-003, QA-INP-021, QA-INP-027 and the other timing items (behaviour draft §14.3: PC-04, PD-01, PS-01, KT-01, TT-01) |
| `down_move_up.json` | The 0.11 manual drag `mouse_button_down(A)` → `mouse_move(B)` → `mouse_button_up(C)` | QA-INP-027 (amendment A14) |
| `tool_text_0_11.json` | The text and `structuredContent` of 134 calls to the installed 0.11 server over MCP stdio, covering all 35 tools, their error paths and the no-session errors | Reference for the `render()` goldens (QA-MCP-003) and the "texts kept verbatim" checks |

## Capture environment

- Image: `docker/e2e.Dockerfile` built from `git archive 7a5d781` (tag `kwin-mcp-e2e:p0-7a5d781`). The installed `kwin_mcp` package was byte-compared with `src/kwin_mcp` of the working tree, and `/app/tests` with `tests/` at `7a5d781`.
- Host: macOS arm64 (OrbStack), running the image natively as `aarch64`.
- Package versions: Debian `kwin-wayland` 4:6.3.6-1, `libei1` 1.3.901-1, `libgtk-3-0t64` 3.24.49-3, `kcalc` 4:25.04.0-1, Python 3.13.5, `mcp` 2.3.0.

## Input timelines (`<scenario>.json`)

### How they were captured

1. One virtual session (`AutomationEngine.session_start`, 1280x800) launched a capture probe: a fixed 1000x640 GTK3 toplevel. Its `realize` handler turns GDK motion compression off, so every `wl_pointer` motion frame becomes one event. Every button, motion, key, scroll and touch event was appended to a JSON-lines log, carrying the compositor event time (`event.time`, ms) and the probe's `g_get_monotonic_time()` at dispatch.
2. The client origin of the probe came from `window_geometry_data()`. All scenario coordinates are probe-local: global = client origin + local. The origin was (140, 92) in this capture.
3. Before each run, `mouse_move` parked the pointer at local (40, 40), followed by 1.2 s of idle time. 1.2 s is longer than the GTK double-click time, so separate runs never merge into one multi-click. The scenario then ran through `AutomationEngine`, which is the code the 0.11 MCP tools call. After another 1.2 s the new log lines were taken as that run's slice.
4. Each scenario ran 5 times. All 5 runs of every scenario produced the identical event sequence (`other_variants` is empty everywhere).

The capture scripts (the probe, the capture driver and the normalizers) are scratch files under `artifacts/golden-capture/`, which is gitignored. This README is the committed record of the method.

### Schema

```json
{
  "scenario": "click_double_ctrl_shift",
  "call": {"tool": "mouse_click", "local": [300, 200], "double": true, "modifiers": ["ctrl", "shift"]},
  "returned_text": ["Clicked left at (440, 292) (double) with ctrl+shift"],
  "repeats": 5,
  "sequence": [{"kind": "motion", "x": 299, "y": 200, "mods": [], "held": []}, "..."],
  "gaps_ms": [{"from": 0, "to": 1, "mono": {"min": 0.17, "median": 0.22, "max": 0.43},
               "event_clock": {"min": 0.0, "median": 0.0, "max": 0.0}}, "..."],
  "call_start_to_first_event_ms": {"min": "...", "median": "...", "max": "..."},
  "last_event_to_call_return_ms": {"min": "...", "median": "...", "max": "..."},
  "first_to_last_event_ms": {"min": "...", "median": "...", "max": "..."},
  "other_variants": []
}
```

- `sequence[*].kind` is one of `motion`, `button_press`, `button_release`, `gtk_double_press`, `gtk_triple_press`, `key_press`, `key_release`, `scroll`, `touch_begin`, `touch_update`, `touch_end`.
  - `gtk_double_press` and `gtk_triple_press` are GTK's synthesized `GDK_2BUTTON_PRESS` and `GDK_3BUTTON_PRESS`. They are kept because they show that GTK counted the clicks as one multi-click. A comparison that uses a probe without them should drop them from both sides.
  - Crossing events (`enter`/`leave`) are excluded.
- Fields per event:
  - `button`: `left`, `middle` or `right`.
  - `key`: the GDK keyval name, for example `Control_L` or `T`.
  - `x`/`y`: probe-local logical px.
  - `mods`: the active modifiers before the event (sorted).
  - `held`: the pointer buttons held before the event.
  - Scroll events carry `direction`. Smooth ones also carry `dx`/`dy` (GTK units: 0.11 sends 15 px per unit, which GTK reports as 1.5 per unit) and `is_stop`.
  - Touch events carry `touch`, the finger slot. Slots restart at 0 for each gesture.
- `gaps_ms[i]` is the interval between `sequence[i]` and `sequence[i+1]`. `mono` uses the probe dispatch clock; `event_clock` uses the compositor timestamps, at ms resolution. The statistics cover the 5 runs.
- `last_event_to_call_return_ms` is slightly negative for most scenarios: the engine call returns before GTK dispatches the last event. That matters for frame-capture anchoring (QA-CAP-010).

### How tests should compare (amendment A15)

The event sequence must match the golden exactly: kinds, order, button, modifiers, keys and probe-local coordinates. Each interval must be at least the golden `mono.min` minus 10 %, and at most 3 times the golden. Do not use ±N ms windows. Each bound may hold on either receive-side clock: the probe's dispatch clock (`mono`) or the compositor's `event_time` (ms resolution, 1 ms of rounding allowed). The lower bound also allows 1 ms of per-event delivery lag, because a 10 ms sender sleep was observed as 9.08 ms at the probe.

## Tool text (`tool_text_0_11.json`)

### How it was captured

The capture used the installed `kwin-mcp` entry point inside the same image, driven through `tests/e2e/mcp_harness.py::running_mcp_server` as of `7a5d781`, in this order:

1. Every session-bound tool without a session.
2. A virtual session with KCalc and the clipboard enabled: every tool, including bad arguments and error paths, plus KWrite through `launch_app`.
3. Two more virtual sessions: one with retention flags and one without an app.
4. A test-owned live KWin (`tests/e2e/session_harness.py::live_kwin`) for `session_connect`, including the live `window_close` refusal.
5. The nested Xvfb/X11 KWin (`tests/e2e/visual_harness.py::nested_visual_kwin`) with `KWIN_MCP_X11_SCREENSHOT=1`, for successful `screenshot` and frame-burst texts. The virtual session in this container has no ScreenShot2, so its `screenshot` calls record the 0.11 failure text.

Each entry has these fields: `label`, `tool`, `arguments`, `is_error`, `content_types`, `text` (all `TextContent` joined with `\n`) and `structured` (the raw `structuredContent`; 0.11 wraps plain-text tools as `{"result": text}`).

### Placeholders

| Token | Replaces |
|---|---|
| `<DIR>/<name>` | the directory part of a temporary path (`/tmp/...`, `/run/user/N/...`); the file name is kept |
| `<TIMESTAMP>` | the `YYYYmmdd_HHMMSS` part of screenshot and frame file names; the same-second `_N` collision suffix of `screenshot_*` files is dropped |
| `kwin-mcp-<kind>-<RAND>` | `mkdtemp` suffixes |
| `<WAYLAND_DISPLAY>`, `<DBUS_ADDRESS>` | per-run socket names and bus addresses |
| `PID=<PID>`, `Available PIDs: [<PIDS>]` | process ids |
| `(<SIZE> KB)` | PNG sizes |
| `{<WINDOW_n>}` | KWin window UUIDs, numbered by first appearance |
| `<DBUS_MACHINE_ID>` | the `GetId` reply |
| `"pid": "<PID>"`, `"size_kb": "<SIZE>"` | the same values in `structured` |

One call was dropped: `read_app_log` on KWrite's own log, because its content is KWrite's timing output. Element coordinates and window geometry are kept as observed. They depend on the KWin and KCalc versions in the image, so compare formats and fields, not the numbers, when the environment differs.
